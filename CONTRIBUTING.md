# Contributing to ProductForge

Thanks for helping. ProductForge is built with the method it generates: work happens in
**phases** (see [`plans/v1/`](plans/v1/README.md)), each small enough for one session, with tests,
acceptance criteria and a ledger update.

## Before you start

1. Read [`CLAUDE.md`](CLAUDE.md) — the golden rules are not optional (stages enforced, evidence
   separate from inference, scripts do arithmetic, staging-only writes, stdlib-only runtime,
   guardrails).
2. Set up: see [`DEVELOPMENT.md`](DEVELOPMENT.md). `make check` must be green before and after.

## How to change things

Follow the **extension recipes** in [`CLAUDE.md`](CLAUDE.md#extension-recipes) — new artifact, new
finding code, new config knob, new gate condition, new delegated capability, new command. Each
names every place that must change together (catalog, validator, overlay fixture, reference docs,
plan tables, tests).

- **Fixtures** are generated by `tests/fixtures/build_tasklet.py`; edit the generator, never the
  snapshots (`make fixtures-check` catches drift). `examples/tasklet/` is generated the same way.
- **Every finding code** has one `tests/fixtures/invalid/<CODE>.md` overlay that yields exactly
  that code, and a row in `skills/productforge/references/record-format.md`.
- **Prompts** (SKILL.md, references, agents) have contract tests; keep SKILL.md under 400 lines —
  stage procedures belong in `references/commands-*.md`.
- **Never** put real third-party content in fixtures, examples or docs — synthetic `.example`
  products only; dogfood reports carry aggregates and paraphrase.

## Proposing larger work

Write a phase file from `templates/plans/phase.md` (the §16.2 headings verbatim) and add it to the
ledger; `phaselint` checks ProductForge's own plans in CI (`tests/e2e/test_dogfood_own_plans.py`).
